# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Is

The **Libre Listener Wallet** is a zero-infrastructure, non-custodial Bitcoin Lightning wallet that runs inside browser/PWA sandboxes (and native mobile wrappers) for the Podcasting 2.0 / Value-for-Value (`v4vmusic.com`) ecosystem. It wraps **LDK (Lightning Development Kit) WASM**, persists node state in IndexedDB, opens just-in-time channels via LSP protocols, and sends V4V "boost" payments as keysend with bLIP-10 TLV metadata.

> Experimental: not production-ready. The README warns loss of funds is likely.

## Architecture

TypeScript monorepo (`packages/*`). Cross-package imports go through package **names**, never relative paths.

- **`packages/shared`** (`@libre/shared`) — single source of truth for protocol types: `WalletConfig`, NWC request/response, LSPS1/LSPS2 JSON-RPC shapes, V4V utils, Zod schemas, `PaymentRecord` + the pure `paymentRecordsToNwcTransactions` mapper (NIP-47 `list_transactions`: sat→msat, ms→unix-sec, type/time filter + paginate) + `NWC_ALWAYS_ALLOWED_METHODS` (`get_info` + `list_transactions`, never allowlist-gated — read-only, exposes no funds). Anything shared between SDK and gateway lives here; do not duplicate type signatures across packages. Also home to three dedup'd cores (2026-07-07 refactor): **`strict-int.ts` `parseStrictInt`** — THE strict integer parse behind every sat amount/limit field (`parseMaxAmount`, the NWC zod `intField`, example-app `parsePositiveIntSats`, PWA `parseNwcLimit`, extension `parseCapInput` all delegate; never hand-roll `parseInt`/`Number()` at a spend boundary — blank/`"1,000"`/`"1e9"`/`"007"` must reject, not coerce); **`error-code.ts` `errorMatchesCode`** — the one boundary-stable matcher (`.code` OR code-token in a flattened `.message`) behind `isNodeAlreadyRunningError`/`isChannelStateRegressionError`/`isCrossDeviceLockError`; **`gateway-auth.ts`** — the push-auth wire contract (kind 27235, tag names, content marker, 300s max-age, `buildGatewayAuthTemplate` + pure `verifyGatewayAuth` with `verifyEvent` injected), imported by BOTH the SDK signer and the gateway verifier so the two ends cannot drift.
- **`packages/libre-listener-wallet`** (`@libre/listener-wallet`) — the client SDK. The `LibreListenerWallet` class (`src/index.ts`) adapts LDK's low-level bindings into a simple API: `start()`, `stop()`, `connectPeer()`, `createInvoice()` (one shared private `buildInvoice()` behind it, `requestLSPS2Invoice()`, and NWC `make_invoice`; buildInvoice force-appends a last-hop route hint via bolt11-hints.ts/hint-selection.ts when LDK omits hints (LDK hints nothing when ANY public channel exists, stranding an unannounced leaf node — external pathfinders refuse to route to it; the transformer re-signs with the node key and is payee-locked)), `sendKeysendPayment()` (the single keysend path — NWC `pay_keysend` routes through it), `syncGossip()`, `onStateChanged(cb)` (fires when channel state is persisted), read-only `getChannels(): ChannelInfo[]` / `getBalance(): { spendableSat, receivableSat }` (mapped from LDK `list_channels()` via the pure `mapChannelDetails`/`sumBalance`; summed over **usable** channels), **forward-only payment history** (PR #15: `getPayments(): PaymentRecord[]` + `notePendingPayment()`, backed by `PaymentLogger` in `payment-log.ts` — one non-critical `tx_<hash>` key per record, unbounded + never backed up, rehydrated at `start()` via `storage.keys()` and finalized from an `instanceof` event demux (`Event_PaymentSent`/`Event_PaymentFailed`/`Event_PaymentClaimed`); the single source of truth behind the extension's Transaction-history card AND NWC `list_transactions`), and encrypted backup/recovery: `exportState({ passphrase? })`, `importState(envelope, secret)` (secret = passphrase, 64-hex seed, or 24-word BIP39 recovery phrase — normalized to hex via `seed-phrase.ts`; auto-detects format; enforces network match), `verifyBackup(envelope, secret)` (decrypts WITHOUT writing storage — used to prove a backup is restorable before funding; returns `{ ok, hasSeed, seedMatches, network, entryKeys }`), and **force-close sweep**: `setSweepDestination(scriptPubKey?)` sets where reclaimed funds go, and on `Event_SpendableOutputs` (a channel close) the SDK sweeps the claimable on-chain outputs there via `PhantomKeysManager.as_OutputSpender().spend_spendable_outputs(...)` → esplora broadcast (built synchronously in the event so the descriptors stay valid; only the tx bytes broadcast async). If no sweep address is set (or the build fails) the handler returns `Err(ReplayEvent)` so LDK re-delivers the event until it's actually swept — funds are never dropped (proven on mainnet recovering a force-closed `to_remote`). Supporting modules: `nwc-manager` (takes `{logger,storage,network}` via its constructor — no reaching into wallet internals; emits **NIP-47 `payment_sent`/`payment_received` notifications** (kind 23196, advertised in `get_info` + the 13194 info event) so apps reconcile a settlement that landed after their request timed out, and **caps the synchronous settlement-await at 90s** so a stuck HTLC can't freeze a client's request chain — see `awaitWithTimeout`; the debit-at-initiation → refund-on-definitive-failure budget policy is ONE `debitBudget`/`awaitSettlementCharged` pair shared by `pay_invoice` AND `pay_keysend`, with the timeout discriminated by error IDENTITY — never message text, which a rewording would silently flip into a cap bypass), `lsps-client`, `esplora-client`, `crypto-utils`, `state-backup` (backup envelope crypto — see below), `seed-phrase` (BIP39 24-word recovery phrase ↔ the raw 32-byte `ldk_seed`, a reversible encoding via `@scure/bip39`: `seedHexToMnemonic`/`mnemonicToSeedHex`/`isValidSeedMnemonic`/`normalizeBackupSecret`; `decryptAndParse`+`verifyBackup` normalize a phrase→hex up front so a phrase works anywhere a seed secret is accepted — the on-disk seed format + envelopes are UNCHANGED. **Raw-seed derivation is deliberately kept**: the 24 words encode the 32-byte entropy AS the node seed, so they restore THIS wallet + any wallet that treats BIP39 entropy as the raw seed, but NOT a standard HD wallet (Phoenix/BlueWallet/LND run words→BIP32 → different keys). Never migrate existing seeds to HD derivation — it would orphan funded wallets), `indexed-db-storage`, `storage-cache`, `peer-reconnect` (exponential-backoff delay calc), `bolt11-hints` + `hint-selection` (invoice route-hint transformer — see the no-route gotcha below; proven live: Strike/Zeus/Primal all pay post-fix). **Peer auto-reconnect:** `connectPeer` records "desired" peers and `handleDisconnect` redials them with exponential backoff (1s→2s→…cap 30s) while the node runs (`stop()` cancels pending redials) — a dropped peer otherwise silently disables sending ("0 first hops"). **Duplicate-dial guard (fixed 2026-07-05, seen live on mainnet):** two concurrent `connectPeer` calls to the same pubkey (app startup redial racing `redialChannelPeers`) both passed the already-connected check; the duplicate's registration overwrote the healthy descriptor in `connectedPeers`, LDK killed the dupe (`Got second connection with <peer>, closing`), `handleDisconnect` deleted the map entry — orphaning the original still-live connection — and the redial loop minted a fresh duplicate every second forever (peer count flapping 1↔2 while channels stayed usable; backoff never grew because each "successful" connect reset it). Fix: `connectPeer` coalesces concurrent dials per pubkey (`pendingDials`), the already-connected check + the redial timer consult LDK's `list_peers()` ground truth (`ldkHasPeer` — timer/call contexts ONLY, never synchronously inside an LDK callback per the re-entrancy trap below), and `getConnectedPeers()` returns the union of the descriptor map and LDK's handshake-complete list so status displays can't under-report after map drift. Pure decision in `peer-reconnect.ts` `shouldRedialNow`; race pinned by `peer-dial-dedup.test.ts` (real LDK, mock transport). **Cross-restart reconnect:** `connectPeer` also persists a **peer address book** (pubkey→{host,port}, storage key `peer_addresses`, non-critical/not-in-backup) because LDK stores no peer addresses and the in-memory desired-peers list is empty on a fresh start; `start()` then calls `redialChannelPeers()`, which loads the book and auto-redials every `list_channels()` counterparty it has an address for (pure `channelPeersToRedial`/`parsePeerAddressBook`, gated by `autoReconnectPeers`, fully best-effort + fire-and-forget). This is what keeps a funded channel alive across a browser reload WITHOUT a manual reconnect — previously only the app's single configured peer was redialed, so a channel opened to a *different* peer (e.g. an LSPS1 provider like Olympus) went inactive on reload until connected by hand. `WalletConfig` extras: `announceChannels`, `alias` (broadcast a node_announcement), `trustedZeroConfPeers`, `rapidGossipSyncUrl`, `autoReconnectPeers` (default on; set false to disable). Built to CJS+ESM via `tsup`. **Fund-safety invariants (do not regress):** `IndexedDBStorageProvider.getItem` rejects on a DB/transaction error (only genuine key-absence returns null) — flattening errors to null let `start()` mistake a broken store for a new wallet and overwrite the seed. `StorageCache` (which acks LDK's synchronous `KVStore.write`/`remove` before the async IndexedDB commit) flips to a **degraded** state on the first persist rejection and thereafter returns `IOError` from every write, so LDK stops advancing channel state instead of acting on storage it can't trust (`isPersistenceHealthy()`); it takes an optional `Logger`. `start()` **throws** if a stored `channel_manager` fails to decode (never bootstraps a fresh empty manager over real state → force-close). `start()` also **throws** an exported `ChannelStateRegressionError` (`state-highwater.ts`, code `CHANNEL_STATE_REGRESSION`) BEFORE any peer dial if a loaded monitor's `get_latest_update_id()` is behind its persisted `monitor_update_highwater` mark, wires monitor persistence through `createDurablePersist` (`durable-persist.ts`) so `ChainMonitor.channel_monitor_updated` only fires after `StorageCache.flush()` durably lands (root fix for the regression), and — given an injected `acquireRunLock` — throws `NodeAlreadyRunningError` (code `NODE_ALREADY_RUNNING`) if another context in this origin already holds the per-origin Web Lock; see the single-node-lock gotcha below for all three. `stop()` and `start()`'s failure path share ONE private `teardownRuntime({ persist })` — register any new runtime resource (interval, timer, client) there, never in just one path (a resource leaked on the other path keeps persisting/dialing after the run lock frees → the second-node race). `importState` writes `ldk_seed` **last** for crash-safety. `sendKeysendPayment` never returns `ok:false` once `send_spontaneous_payment` succeeds (the post-send preimage persist is best-effort) — a false failure makes NWC retry and double-pay. **VSS durable off-device replica (opt-in via `WalletConfig.vssUrl`; the apps do NOT set it yet, so it's dormant):** `vss-protobuf.ts` (dep-free proto3 codec — no protobuf runtime in the SW bundle; CLIENT half only — the server-side decode/encode lives in `tests/integration/vss-protobuf-server.ts` next to its only consumer, the in-memory test server), `vss-client.ts` (`VssClient` over protobuf-HTTP to an LDK `vss-server`; `fetchImpl` bound to `globalThis`; typed `VssError`+`isVssConflict`/`isVssNotFound`; `start()` derives ONE store id + client shared by the restore/lease/mirror consumers), `vss-mirror.ts` (`VssMirror` — a best-effort, seed-encrypted mirror of the same `exportState` envelope; **THROTTLE, not a resetting debounce** — a resetting debounce never fires under continuous state changes (the 1s event tick), so VSS would stay stuck at the empty start state — plus **`flush()` on stop()** to hand off the final state). `start()` calls `maybeRestoreStateFromVss` — re-hydrates **only into EMPTY local storage** (via `importState` → then `StorageCache.reload()`, NOT `load()` which no-ops once loaded → the monitors would never load → force-close). **`WalletConfig`: `vssUrl`, `enforceSingleDevice`, `minChannelConfirmations`.** **Cross-device single-instance lease** (`vss-device-lease.ts`/`device-lease.ts`, `CrossDeviceLockError` code `SINGLE_DEVICE_VIOLATION`, `@libre/shared` `isCrossDeviceLockError`): the Web-Locks node lock only covers ONE origin; this VSS-backed lease (compare-and-swap `node_lease` at start, heartbeat, release on stop, **2-min crash takeover**) stops the SAME seed running on two devices at once. VSS-unreachable at startup starts with a WARNING (reliability). Default on when `vssUrl` set. **Streaming-sats latency fix (do NOT regress):** the durable-persist ack pumps `PeerManager.process_events()` right after `channel_monitor_updated` — without it each monitor-gated commitment step waited for the 10s peer tick and an NWC keysend took 15-30s to settle (killing V4V streaming throughput); with it, ~1s. **NWC pairing cap:** `MAX_NWC_CONNECTIONS = 10` (`createConnection` rejects the 11th; expired pairings auto-pruned on init + create).
- **`packages/libre-nwc-push-gateway`** (`@libre/nwc-push-gateway`) — stateless Express server (`LibreNWCPushGateway`) that subscribes to Nostr relays and sends Web Push to wake offline PWAs for NWC/NIP-47 requests. Also exposes a **CORS-enabled RGS passthrough** (`GET /rgs/snapshot/:timestamp`) that fetches the LDK gossip snapshot server-side and re-serves it with CORS, so browsers can populate the network graph for multi-hop routing (see the RGS gotcha below). SQLite-backed (`better-sqlite3`), CJS build. Deployed on Railway (`nwc-push-gateway-production.up.railway.app`). **SSRF guard:** `/api/register` validates `relayUrl` (must be `wss://` to a non-private host) and `subscription.endpoint` (must be `https://`) via `isSafeRelayUrl`/`isSafePushEndpoint`, caps distinct relay listeners (`maxRelayListeners`), and refuses private/loopback hosts unless `allowPrivateRelays: true` (set only in tests) — a public box must never be coaxed into dialing internal services. `ensureRelayListener` re-checks before opening any outbound connection, and the RGS `:timestamp` is `^\d+$`-validated before URL interpolation. **Signed push-auth (`requirePushAuth`, default true):** `/api/register` + `/api/unregister` require a NIP-98-style signed event (kind 27235, bound to action+relay+endpoint+freshness) proving control of `walletPubkey` — without it anyone who scrapes a wallet's public pubkey off a relay could hijack or delete its push subscription. Clients sign via the SDK `NwcManager.buildGatewayAuth`; verified server-side by `verifyGatewayAuth` — **the wire contract (kind/tags/max-age + builder/verifier) lives in `@libre/shared` `gateway-auth.ts`**, imported by both ends. Extra hardening: IPv4-mapped-IPv6 SSRF unwrap (`isPrivateHost` — kept in sync BY HAND with ws-bridge's copy, see that entry), RGS proxy fetch-timeout+size-cap+TTL-cache (the cache stores the **in-flight promise**, so an app-start burst of concurrent misses for one timestamp coalesces onto a single upstream fetch — never one 32MB buffer per request — a rejected fetch is dropped immediately, and expired entries are evicted on lookup, not left resident until the size cap), `maxSubscriptions` row cap, generic 500s (no internal-error leak). **Breaking:** deployed clients must redeploy to sign, or their register 401s.
- **`packages/libre-lsps2-server`** (`@libre/lsps2-server`) — a **regtest-only dev LSP** that funds the listener through the app's existing LSPS2 flow (`lsps2.get_versions`/`get_info`/`buy`). **Real HTLC-interception JIT (as of the `feat(lsps2)` work):** on `buy` it opens an **instant zero-conf** channel from `libre-lnd` to the client (`LndRestClient.openZeroConfChannel`, ANCHORS), reads lnd's own alias (`findZeroConfAlias` → `alias_scids[0] ?? peer_scid_alias`, decimal), returns it as `jit_channel_scid`, and registers the JIT in an in-memory `JitStore` keyed by that alias. A **gRPC `HtlcInterceptor`** (`LndGrpcInterceptor`, `@grpc/grpc-js` + a minimal embedded `router.proto` with lnd v0.18.5 field numbers — no vendored proto tree; needs lnd's `tls.cert` + macaroon, `ssl_target_name_override: "localhost"`) holds every forward; `decideIntercept` (pure, `fee.ts`/`jit-store.ts`) skims the one-time opening fee via `RESUME_MODIFIED` (`out_amount_msat`, needs lnd ≥ v0.18.4 — hence the v0.18.5 bump) and passes everything else through. The client (`requestLSPS2Invoice`) forces the intercept scid into the invoice route hint (`prioritizeHints`, no longer discarded) and sets `accept_underpaying_htlcs(true)`. Express on `127.0.0.1:9099` (`POST /lsps2`); `server.cjs` wires the store + interceptor (needs `LND_TLS_CERT_PATH`, default `/tmp/libre-lnd-tls.cert` — extract via `docker exec libre-lnd cat /root/.lnd/tls.cert > /tmp/libre-lnd-tls.cert`). **Interception + skim proven end-to-end on regtest** by `packages/libre-listener-wallet/src/tests/integration/lsps2-jit-intercept.test.ts` (needs `docker compose up -d` incl. the second **`lnd-payer`** node — lnd only fires the interceptor on FORWARDED htlcs, so the payment must originate from a separate node routing `payer → LSP → client`, not lnd paying its own invoice). **Known remaining gap (documented, not a code bug):** the client does NOT end up *claiming* the skimmed HTLC — lnd's `RESUME_MODIFIED` lowers the amount but the HTLC reaches LDK 0.1.x with `skimmed_fee_msat: None`, so LDK fails the final hop `FINAL_INCORRECT_HTLC_AMOUNT` despite `accept_underpaying_htlcs=1` (LDK doesn't infer the skim from the amount shortfall / expects a skim signal lnd doesn't send). The client trace confirms the skim landed (`UpdateAddHTLC amount_msat: 19750000` for a 20000-sat invoice). Follow-up: bridge the lnd↔LDK skim signalling (e.g. the interceptor's `out_wire_custom_records`) or switch the fee to a route-hint hop fee (payer pays amount+fee, client receives full amount — no underpayment). The old eager-confirmed-channel path (`openChannel`/`mineBlocks`/`findChannelScid`, `openAndConfirm`) is gone; `BitcoindClient` remains for other uses.
- **`packages/example-app`** (`@libre/example-app`) — Vite PWA playground. `main.ts` is being slimmed into a bootstrap that wires feature modules (`web-push.ts`, `nwc-ui.ts`, `v4v.ts`, …) plus `core/` (`logger.ts`, `ui-helpers.ts`, `app-context.ts`). The remaining handlers (node start/stop, peer-connect, lsp-capacity, receive, backup/drive, network-config, seed) are still inline in `main.ts` — extract them the same way. `core/persistent-storage.ts` (`ensurePersistentStorage()`) is the one app-layer module that may touch `navigator`. The **mainnet preset + Google Client ID read from a gitignored `.env.local`** (`VITE_MAINNET_PEER`, `VITE_MAINNET_BRIDGE`, `VITE_GOOGLE_CLIENT_ID`, `VITE_MAINNET_RGS` = the gateway `/rgs/snapshot` URL). `tsup.config.ts` bundles `src/service-worker.ts` into `public/` separately from the Vite build. Has its own vitest setup (`pnpm --filter @libre/example-app test`). **Page layout (`index.html`):** a focused top **`.setup-zone`** (the only thing you set up first) — a full-width **status strip** (`.stat-grid`: node id, peers, spendable/receivable, channels, routing graph) over three `.card` panels **Wallet & Seed / Node / Backup & Recovery** — sits above the **"Protocol & Feature Tests"** grid (`.dashboard-grid`) holding the rest (LSP, LSPS2, LSPS1, V4V audio, Receive, Boost, NWC, Web Push, Console). The status strip is the live **balance + channel-status view** (`refreshWalletView()` reads `getBalance()`/`getChannels()`, refreshed on start/`onStateChanged`/LDK-events + a 5s poll, cleared on stop) with per-channel **active/ready/pending** badges (`isUsable`/`isChannelReady`). **Node connection lives in the Node panel:** it leads with the essentials — Network, Start/Stop, **Connect Peer** (`#connect-lsp-btn`), auto-start — and the set-once endpoints/peer config (the **preset** `#lsp-preset`, node **`pubkey@host:port`** `#lsp-conn-str`, **bridge URL** `#ws-bridge-url` + websockify note, **Esplora URL** `#esplora-url-input`) are tucked into a collapsible `<details class="advanced-settings">` "Connection settings" so the panel stays simple (defaults auto-fill, so the normal flow is Start → Connect Peer without opening it). The test-grid card keeps only the LSP JSON-RPC URL (`#lsp-api-url`) for JIT. The status strip's **Node ID** tile has a **Copy** button (`#copy-node-id-btn`) — the pubkey you paste into your own node's `openchannel --node_key=` to open a channel to the browser wallet (a browser node has no socket/listening address, so it's opened to as an already-connected inbound peer, by pubkey only). **Auto-connect is gated** (`main.ts`): a wallet auto-reconnects its peer on load ONLY when channel state already exists (keeps a funded channel alive across reloads); a brand-new/empty wallet starts but does **not** auto-peer — so a shared deployment doesn't silently peer every visitor to the configured node, and opening the first channel needs an explicit Connect Peer click. The LSPS1 card has a **provider selector** (`#lsps1-provider`: Megalith / Olympus-ZEUS — real mainnet LSPs) + a **channel lease-duration picker** wired to `purchaseLSPS1Capacity`'s `channelExpiryBlocks` (clamped to `[1, max]`, defaults to MAX — longest channel life per open fee; `announceChannel` defaults false since a browser node has no reachable address). The picker is **cost-aware** (`core/lsps1-provider-ui.ts`, pure + tested): a live provider summary (cost/lease character + sat bounds), amount validation with a **smart redirect** (Megalith rejects <150k → suggests Olympus, which serves 100k+), lease durations **disabled beyond the selected provider's max** (Megalith ~3mo greys out 6/12mo; "Longest available" states the real months), and an **opening-fee readout** after Get Quote & Order. `LSPS1_REST_PROVIDERS` now also carries `minChannelSat`/`maxChannelSat`/`maxLeaseBlocks`/`leaseMonthsApprox`/`costNote` (live-verified) driving that picker. **`purchaseLSPS1Capacity` now speaks the LSPS1 REST binding** (bLIP-51 HTTP, not the dev server's JSON-RPC): `Lsps1RestClient` (`lsps1-rest-client.ts`) hits `GET /get_info` (bounds + live peer `uris`), dials the LSP node read from `uris`, `POST /create_order` (bLIP-51 `public_key`, sat amounts as strings), and returns `{ orderId, invoice, feeTotalSat, onchainAddress, lspPeerUri }`; poll `getLSPS1Order(apiUrl, orderId)` after paying until `order_state: COMPLETED`. 0-conf requested only when the LSP offers it AND its pubkey is in `trustedZeroConfPeers`. Provider bases in `@libre/shared` `LSPS1_REST_PROVIDERS` (Megalith `megalithic.me/api/lsps1/v1` — 150k–16M, instant 0-conf; Olympus `lsps1.lnolymp.us/api/v1` — 100k–10M, 3-conf, ~12mo lease). Live-verified `get_info` against both mainnet endpoints. **Browser caveat (resolved):** a browser node reaches the LSP's node through the **allowlisted multi-target `@libre/ws-bridge`** — the transport appends `?target=host:port`, so the LSP's node must be in the bridge's `BRIDGE_ALLOWLIST` (Megalith/Olympus are). **Proven live end-to-end on mainnet:** create_order against Megalith returned a real fee+invoice (13,126 sat for a 150k channel). The dial is still best-effort + logged. **LSPS2 JIT — ATTEMPTED + PARKED (branch `feat/lsps2-jit-m1`, NOT on master):** built the full LSPS0 custom-message transport over BOLT8 (peer msg 37913), but real mainnet LSPs stay silent — blocked by an LDK 0.1.0 WASM binding bug (see the "LDK 0.1.0 can't do custom peer messages" gotcha below + the [[mainnet-lsp-integration]] memory). **Verdict: not worth the LDK re-engine for this product** — the cheap BOLT8-only LSPs (e.g. Lnserver ~5k/2M) only serve LARGE channels; a listener wants a SMALL channel (100–500k), where Megalith(150k)/Olympus(100k) are the only fit AND the cheapest that exist. ### Core design patterns (enforced)

- **Dependency injection / platform abstraction:** The SDK must NOT import platform modules (`fs`, `window`, React Native `SecureStore`) directly. Storage, WebSocket transport, and logging are injected as interfaces (`SecureStorageProvider`, `WebSocketStreamProvider`, `Logger`) via the wallet constructor. Web injects IndexedDB; mobile injects Keychain.
- **No stateful singletons:** Never `export const node = new LDKNode()`. Instantiate the node inside a class instance so tests can run concurrently and re-init cleanly.
- **No hardcoded env in the SDK:** All config (network, Esplora endpoint, whitelisted relays/LSPs) is passed into the constructor — no `process.env` reads inside the library.
- **Barrel exports only:** Import from package `index.ts`, not deep relative paths.
- **Errors:** No silent catches. Log via the injected `Logger` and rethrow or return `{ ok: false, error: string }`.

- Key `7629169`: UTF-8 JSON `BoostRecord` (bLIP-10) — **not** hex-encoded.

### Backup format (`state-backup.ts`)

- **v2 (current) = envelope encryption.** A random 32-byte DEK encrypts the `BackupPayload` (AES-256-GCM); the DEK is wrapped to **both** a passphrase (PBKDF2-SHA256, 600k iters, random salt) and the seed (HKDF-SHA256, info `libre-wallet-backup-kek-v2`), so **either secret independently decrypts** the backup. `serializeAndEncrypt(payload, { passphrase, seedHex })` emits v2.
- **v1 (legacy) = seed-only** (HKDF info `libre-wallet-backup-v1`, AES-GCM). `serializeAndEncryptV1(payload, seedHex)` still exists; `decryptAndParse(envelope, secret)` auto-detects v1/v2. `exportState()` with no passphrase emits v1 (what the example app + browser-extension both ship today — so their backups are seed-encrypted, i.e. **a passphrase never unlocks an extension/PWA backup**).
- **The restore `secret` also accepts the 24-word BIP39 recovery phrase.** `decryptAndParse` (and `verifyBackup`) call `normalizeBackupSecret(secret)` first, which converts a valid 24-word phrase to its 64-hex seed; hex + passphrase pass straight through. So for a v1 backup the unlock secret is the **hex seed OR its 24-word phrase** (equivalent); passphrase only applies to a v2 backup that was actually created with one. The storage contract is untouched — a frozen-envelope test proves the golden v1/v2 backups still decrypt via the seed's derived phrase.
- `BackupPayload.entries` holds `ldk_seed` + `channel_manager` + monitor keys + `state_version` — i.e. the seed is *inside* the (encrypted) backup. The top-level (non-monitor) key set is pinned as `BACKUP_DIRECT_KEYS` (`backup-keys.ts`); `exportState` appends the monitor keys from `ldk_keys_index` and flushes **only** the channel manager first (`persistChannelManagerState`), not the graph. **`network_graph`/`scorer` are deliberately EXCLUDED** — they're re-derivable (the graph re-syncs from RGS + rebuilds from gossip, the scorer rebuilds over use), and the graph alone is 20MB+; dropping them shrinks a backup from ~23MB to a few KB. On restore they're simply absent and `start()` creates fresh ones (the brand-new-wallet path, `index.ts`); **older backups that still contain them restore fine** (backward-compatible — proven by the frozen golden-envelope tests + the regtest `recovery.test.ts` funded-channel export→wipe→restore→keysend cycle), so no migration was needed. All WebCrypto; no deps. The DB-not-namespaced-by-network gotcha means a backup's `network` is checked on import.

## Critical Guardrails

- **Absolute key isolation:** Seed phrases, private keys, and unclaimed-HTLC preimages must never leave the client sandbox — never over sockets, HTTP, or logs. Backups must be encrypted locally first.
- **Zero-custody gateway:** The push gateway must never hold node keys or NWC shared secrets; it routes blind, encrypted Nostr envelopes only.
- **DB isolation:** The gateway uses its own standalone SQLite/Postgres DB — never the host app's database.
- **Zero-conf LSP vetting:** Accept 0-conf JIT channels only from trusted LSPs. Enforced on the acceptance side via `WalletConfig.trustedZeroConfPeers` (allowlist of counterparty pubkeys); non-allowlisted peers fall through to a normal, confirmation-gated channel. Never 0-conf from random gossip nodes.
- **Localhost binding:** All docker/testing services map ports to `127.0.0.1` only.
- **One LDK node per origin, and never advance state on an unconfirmed write:** `start()` enforces this via the single-node lock (`NodeAlreadyRunningError`), the channel-state regression halt (`ChannelStateRegressionError`), and durable-before-advance monitor persistence (`createDurablePersist`) — see the 2026-07-06 force-close gotcha below for why all three exist.

## Known limitations & gotchas (hard-won — read before debugging "it broke")

- **Two mainnet channels force-closed 2026-07-06 from offscreen-persistence loss — fixed by a three-layer defense (PRs #17/#18/#19).** Diagnosed from lnd logs: `channel_reestablish` arrived at tail height 0 vs. real 180 → a stale/reset persistence layer replayed old channel state at the peer, which is a BOLT2 data-loss protocol violation → the peer force-closed (funds recovered via the sweep address, `StaticRemoteKey` `to_remote`). **Layer A (halt on regression, PR #17):** `start()` throws `ChannelStateRegressionError` BEFORE dialing any peer if a loaded `ChannelMonitor.get_latest_update_id()` is below a persisted per-channel high-water mark (`monitor_update_highwater` storage key — non-critical, NOT in the backup, advanced during operation incl. channels opened mid-session via `ChainMonitor.list_monitors()`, cleared on `importState`); pure logic (`parseHighwater`/`mergeHighwater`/`findRegression`/`pickUpdateId`) lives in `state-highwater.ts`, turning a would-be data-loss reconnect into a safe HALT + restore-from-backup prompt. **Layer C (durable-before-advance, PR #18) — the ROOT fix:** `createDurablePersist` (`durable-persist.ts`) wraps the existing `MonitorUpdatingPersister` so every monitor persist returns `ChannelMonitorUpdateStatus::InProgress` and only calls `ChainMonitor.channel_monitor_updated` AFTER `StorageCache.flush()` resolves (flush rejects immediately if the cache is `degraded`) — so LDK can never advance past a write that didn't durably land, closing the exact offscreen-reap → stale-reload → force-close hole. On-disk monitor format is unchanged; proven by a docker POC that the LDK 0.1.0 WASM binding actually honors `InProgress` (a payer's HTLC stayed IN_FLIGHT through a storage hold, settling only on release). **Single-node lock (PR #19):** `@libre/shared` `acquireWebNodeLock(name)` (Web Locks `navigator.locks`, `ifAvailable`, degrades to a no-op release when unavailable so it never blocks a legit start) plumbed through a `start()` constructor option — a second context in the SAME origin (e.g. a PWA's page vs. its service worker, both hammering the same IndexedDB) gets `NodeAlreadyRunningError` (code `NODE_ALREADY_RUNNING`) instead of racing the first. All three errors carry a boundary-stable `code` mirrored into `.message` (`isChannelStateRegressionError`/`isNodeAlreadyRunningError` in `@libre/shared`) so the extension's `chrome.runtime`-flattened errors still match. **Cross-device gap — now closed by the VSS device lease (when `vssUrl` is set):** the Web-Locks single-node lock only covers ONE origin; the SAME seed on a second device (extension + PWA + phone) is invisible to it. `WalletConfig.enforceSingleDevice` (default true when `vssUrl` set) claims a `node_lease` in the shared VSS store (same seed → same store) via a compare-and-swap at `start()` BEFORE dialing; a second device that sees a live lease throws `CrossDeviceLockError` (code `SINGLE_DEVICE_VIOLATION`, `isCrossDeviceLockError` in `@libre/shared`) instead of putting a second node on the channel. Heartbeat renews it; stop() releases it; a crashed holder's lease auto-expires after a 2-min takeover window; VSS-unreachable at startup starts with a warning (reliability). See `vss-device-lease.ts`/`device-lease.ts`. WITHOUT `vssUrl` (no shared store) this stays operator discipline — run one instance of a given wallet at a time.
- **NWC keysend settled in 15-30s (V4V streaming throughput ~2/min) until the durable-persist ack pumped `process_events()` (fixed 2026-07-07).** The async durable-persist (Layer C) un-pauses a channel only when `channel_monitor_updated` fires in the flush's promise continuation — but nothing pumped `PeerManager.process_events()` after it, so each monitor-gated commitment-dance step waited for the 10s `peerTickIntervalId`. A keysend needs ~2-3 such steps → 15-30s to settle (payments SUCCEED but BACK UP under 10-20/min streaming — the real cause of streaming degradation, NOT force-close). Fix: `createDurablePersist`'s `onDurablePersisted` callback calls `peerManager.process_events()` right after `channel_monitor_updated` (safe — promise continuation, NOT inside a SocketDescriptor callback, so no re-entrancy trap). Settlement → ~1s. Found only by a soak that MEASURES latency (`soak-nwc-streaming.test.ts`), not a pass/fail one. Do NOT remove the pump.
- **LDK can't hand a LIVE channel between running node instances by state-copy — active cross-device handoff force-closes.** Copying `channel_manager`+monitors (via VSS or a backup) onto a device that ALREADY holds STALE state for that channel doesn't reconstruct it: the monitors don't replace the old ones, so on reconnect LDK sends a "bogus ChannelReestablish ... to force channel closure" ("no such channel"). So `maybeRestoreStateFromVss` re-hydrates ONLY into EMPTY local storage (never over existing state). **Safe multi-device patterns:** (a) MOVE the wallet to a FRESH device — backup/Drive/VSS restore into empty storage WORKS (`restoreWallet`→`importState` brings channel state, not just the seed), then don't run the old device; (b) ONE always-on node + other devices as **NWC clients** (NWC's design — no second node); the device LEASE prevents the simultaneous-use collision. Reproduced + documented by the `it.skip`'d `soak-crossdevice-handoff.test.ts`. Bidirectional shuttling between two live full-node copies is the only genuinely unsafe pattern.
- **Wallet storage IS namespaced by network (fixed).** Each network uses its own IndexedDB (`libre-wallet-<network>`); the example app builds a network-scoped `IndexedDBStorageProvider` (`core/storage-namespace.ts` → `dbNameForNetwork`), auto-migrates the legacy un-namespaced `libre-wallet` DB into the right network DB on first load (`migrateStorage`, idempotent, copies `ldk_seed` last for crash-safety, legacy DB left intact), and disables the network selector while the node runs. Off-page consumers (service worker, web-push simulate) read the active network from a fixed `libre-wallet-meta` pointer (`ACTIVE_NETWORK_KEY`). Historically all networks shared one DB and switching profiles corrupted channel state (`Loaded 0 channel monitors` + a wrong-chain manager) — that's resolved. Each network is an independent wallet (own seed).
- **The example app is deployed to GitHub Pages, and a storage-layer change can orphan a funded wallet.** `.github/workflows/deploy-pages.yml` builds `@libre/example-app` and publishes to `https://chadfarrow.github.io/libre-listener-wallet-monorepo/` on **every push to `master`** that touches `packages/{example-app,shared,libre-listener-wallet}/**` (native Actions Pages pipeline; `vite.config.ts` `base: "./"`; mainnet `VITE_*` come from repo *Variables*). Wallet state lives in that origin's IndexedDB independent of the code, so UI/feature pushes are safe — but renaming a persisted key, changing a DB name, or altering the backup format makes the node unable to find its channel state on next load (**force-close**) or makes existing encrypted backups undecryptable. **Guard (defense-in-depth):** the **storage-contract tests** (`packages/libre-listener-wallet/src/tests/unit/storage-contract.test.ts` + `packages/example-app/src/core/storage-contract.test.ts`) pin every on-disk invariant — DB name format / object store `settings` / version `1`, the `libre-wallet-meta`+`active_network` pointer, the Drive filename, and the backup envelope format via **frozen golden v1/v2 envelopes that must keep decrypting**. `pnpm check:storage` runs just these (unit, no docker/WASM). A **husky `.husky/pre-push`** hook hard-blocks a push when an invariant changed (override: `git push --no-verify`) and warns when any storage-layer file is touched; the **deploy workflow re-runs `check:storage` before build** so a `--no-verify` push (or a clone without the hook) still can't ship a broken invariant — the build fails and production stays on the last good version. When you intentionally change a storage constant, add a migration and update the contract test (incl. regenerating golden envelopes) in the **same commit**.
- **Rapid Gossip Sync is CORS-blocked at the source — solved via a proxy.** `rapidsync.lightningdevkit.org` sends no `Access-Control-Allow-Origin`, so a direct browser `fetch` fails (it only works from Node tests). Without the graph there's **no multi-hop routing** (e.g. a v4vmusic boost to an arbitrary artist fails to find a route). The fix: the **push gateway exposes a CORS-enabled passthrough at `GET /rgs/snapshot/:timestamp`** (`packages/libre-nwc-push-gateway/src/index.ts`) that fetches the LDK snapshot server-side and re-serves it with CORS. The example app points `rapidGossipSyncUrl` at it via **`VITE_MAINNET_RGS`** (resolved mainnet-only by `core/rgs-config.ts`; the LDK RGS server only serves mainnet snapshots), warms the graph on node start, and exposes a manual **Sync gossip** button + a graph-channel-count readout. Live P2P gossip is still disabled (`IgnoringMessageHandler`). Caveat: multi-hop only succeeds if the wallet's channel peer has a **public/announced** path onward (the RGS graph only contains announced channels) — a peer whose only channel is private to the wallet is a routing dead-end.
- **Public Esplora endpoints rate-limit.** `mempool.space` → "Failed to fetch" (CORS/Cloudflare), `blockstream.info` → `429 Too Many Requests` once a Start's burst of block-by-block sync requests (compounded by repeated Starts) trips the limit. The example app now defaults mainnet to `mempool.space/api`; don't spam Start. **Auto-start-on-load is enabled by default** (a wallet should just run) but exposed as an **"Auto-start node on load" checkbox** (persisted in `localStorage` as `libre_autostart`); untick it if public-Esplora rate limits bite on repeated reloads.
- **A browser node has no listening socket** — nothing can dial it. It connects *out* through the **`@libre/ws-bridge`** (an allowlisted multi-target WS→TCP proxy; the transport appends `?target=host:port` so a single bridge reaches the channel peer AND the LSPs — see its package entry) to a peer, and the peer opens the channel back over that existing connection. This is also why *every* channel — even "share your Node ID and have someone open one to you" — requires the browser to dial out first (you become an already-connected inbound peer by pubkey; there's no bridge-free path). Tor-only peers need a `tor` + `socat` (SOCKS4A) + `websockify` chain.
- **Esplora txid byte-order (fixed — was why channels never confirmed in-browser).** LDK hands txids as raw bytes in **little-endian** (internal) order; esplora's REST API addresses txs by **big-endian display** hex (the reverse). `esplora-client.ts` must convert via `ldkTxidToDisplay()` before any esplora lookup (`register_tx`, `register_output`, and the `get_relevant_txids()` query sites) — but **keep little-endian when feeding a txid back to LDK** (e.g. reorg `transaction_unconfirmed`). Symptom of the bug: funding tx confirmed on-chain + lnd sees the channel, but the wallet stays `pending` forever (`isChannelReady=false`), never sends `channel_ready`, so lnd's link stays `active:false` and payments fail `INSUFFICIENT_BALANCE`.
- **Buried-confirmation catch-up (fixed).** `sync()`'s forward loop only confirms txs whose block is in `(bestHeight, tip]`. A funding tx registered **after** its block was already synced — instant regtest mining, or app closed → funding confirms → reopen past the block (a real **mainnet PWA restart race**) — would never confirm. `sync()` runs a catch-up pass (`planBuriedConfirmations`) that confirms watched/registered txs buried at height `≤ bestHeight` at their real height. `sync()` runs every 30s, so stuck channels recover on the next tick.
- **A seed without channel state must never auto-start/connect (force-close risk — fixed).** A bare seed with no `channel_manager` (e.g. a restore that didn't complete, or a seed injected into a fresh origin) that auto-starts will bootstrap a fresh empty ChannelManager, connect the peer, and on the peer's `channel_reestablish` reply "unknown channel" → **force-close the real channel** (this actually happened on mainnet during the web migration). Fix: `example-app/src/core/wallet-readiness.ts` `assessStartReadiness` gates auto-start AND manual Start — a seed with no channel state may start only if created brand-new here (`wallet_created_new` provenance marker). The **force-close sweeper** (`setSweepDestination` + `Event_SpendableOutputs`) is the recovery net if it ever happens; a `StaticRemoteKey` channel's `to_remote` is seed-claimable.
- **The service worker must BUNDLE every dependency (no bare specifiers).** `src/service-worker.ts` is compiled by **tsup** (invoked from the vite `copyLdkWasmPlugin` `buildStart`, so `vite build` — and thus CI/Pages deploy — builds it too) and bundles the full SDK. tsup **auto-externalizes `package.json` dependencies**, so any dep the SW transitively needs must be added to tsup's `noExternal` — otherwise a bare `import … from "x"` survives in the bundle and the browser SW dies with **"ServiceWorker script evaluation failed"** (a browser ServiceWorker can't resolve bare specifiers). This bit us when `@scure/base` was added (pulled in transitively via `nostr-tools`): the fix was adding it to `noExternal`. Debug by evaluating `public/service-worker.js` in a SW-scope sandbox (define `self`/`caches`/`clients`, leave `window`/`document` undefined) — Node resolves bare specifiers so it passes; the browser doesn't.
- **LDK event dispatch MUST use `instanceof`, never `event.constructor.name` (minification silently breaks it — prod-only).** The deployed PWA is minified (Vite/esbuild), which mangles the LDK binding class names — `Event_OpenChannelRequest` becomes e.g. `Fzt` at runtime. So dispatching with `event.constructor.name === "Event_..."` fails on the live site and **no event handler runs**: an inbound channel open is received (`OpenChannelRequest` fires) but never accepted (no `accept_inbound_channel` → no `accept_channel` sent → the opener's `openchannel` spins and times out, funds return on-chain), and the **same trap kills payment-claiming** (`Event_PaymentClaimable`) **and the force-close sweeper** (`Event_SpendableOutputs`) — the whole event system is dead in production. It works in `pnpm dev` because dev isn't minified, so it looks fine locally. Fix (in `index.ts` `handle_event`): dispatch every branch with `event instanceof Event_X` (compares the imported class reference, which survives minification) and import the `Event_*` classes. Guarded by `tests/unit/event-dispatch-minify-safe.test.ts` (source-level — a normal unit test can't catch it since vitest isn't minified). Console symptom: `[LDK Event] Received event:` followed by a mangled name (`Fzt`, `DC`, `WC`, …) and **no** matching accept/claim/sweep line after it. (Cost a long live mainnet debugging session; found from a user console log showing `OpenChannelRequest` received + `Event fired: Fzt` + no accept while ThunderHub spun.)
- **Never call `PeerManager` methods synchronously from inside a `SocketDescriptor` callback — LDK invokes `disconnect_socket()` re-entrantly and the re-entrant call panics (`BorrowMutError` → `unreachable executed`), permanently killing auto-reconnect.** When a peer's ping/handshake times out, LDK's `PeerManager.timer_tick_occurred()` disconnects it by calling our `WebSocketDescriptor.disconnect_socket()` **from within its own call** (the LDK docs literally warn "be very careful about reentrancy issues"). If `handleDisconnect` then calls back into `peerManager.socket_disconnected()`/`process_events()` synchronously, the WASM `RefCell` is still borrowed by `timer_tick_occurred` → `panicked at 'already borrowed: BorrowMutError'` → a WASM `unreachable` trap. On the minified PWA it surfaces as `[Reconnect] peer … attempt N failed: unreachable executed`, and since it fires on **every** redial the channel stays offline forever (peer link down, `getBalance()` reads 0/0 because it only sums *usable* channels) until a manual page reload spins up a fresh `PeerManager`. The transport (websockify bridge) reconnects fine each time — only the LDK handshake traps. Fix (`index.ts` `handleDisconnect`): keep local cleanup (drop from `connectedPeers`, `scheduleReconnect`) synchronous but **defer the `socket_disconnected()`/`process_events()` calls to a `queueMicrotask`** so the in-flight `PeerManager` call unwinds and releases its borrow first; guard with `if (this.peerManager !== pm) return` in case `stop()` freed it meanwhile. Per the LDK docs, `socket_disconnected` after an LDK-initiated `disconnect_socket` is a documented no-op, so deferring is safe for both the tick-initiated and transport-drop (`onclose`/`onerror`) paths. Guarded by `tests/unit/peer-disconnect-reentrancy.test.ts`, which reproduces the panic with real LDK WASM by driving `timer_tick_occurred()` on a never-handshaked (stale) peer — no docker (esplora mocked via MSW at tip height 0 so the initial sync is a no-op). Console symptom: `Disconnecting peer … due to ping/handshake timeout` followed by endless `WebSocket bridge connected` + `attempt N failed: unreachable executed` with the peer never re-established. (Cost a live mainnet session: wallet "just sat there and went offline.")
- **External wallets couldn't pay the browser wallet — "no route" from every payer (fixed: invoices force-append route hints).** LDK's `create_invoice_from_channelmanager` includes route hints ONLY when all channels are private; one PUBLIC channel → zero hints (trace log: "Not including channels in invoice route hints on account of public channel"). A browser wallet is an unannounced-address, historically-offline leaf node, and external pathfinders refuse to route to it from graph data alone — proven live 2026-07-03: Strike, Zeus (embedded), and Primal all failed "no route" on a well-formed 1000-sat invoice with 96k receivable and fresh graph policies, while a direct payment from the channel peer settled fine. Fix: `buildInvoice` post-processes the LDK invoice via `bolt11-hints.ts` — appends an `r` tag built from the channel's real `forwarding_info` (`hint-selection.ts` picks usable channels, capacity-ranked, max 3) and re-signs with the node key (`@noble/curves`; payee-locked: refuses to re-sign an invoice whose recovered payee isn't the provided key). Best-effort: any failure logs + returns the original unhinted invoice. All three payers settle post-fix. Two binding traps pinned by tests: noble v2's `format:"recovered"` signature is **recid-FIRST** while BOLT11 wire order is recid-LAST (reorder required), and the bindings return a **truthy `CounterpartyForwardingInfo` wrapper for Rust `None`** (internal `ptr === 0n`; accessors silently return 0) — naive truthiness fabricated zero-fee hints for channels whose peer hadn't sent a `channel_update` yet (`forwardingInfoFromLdk` detects the null ptr + a zero-cltv belt-and-braces guard). Diagnosis recipe: decode the BOLT11 (npm `bolt11`, dev dep) and look for the `routing_info` tag; LDK trace-logs its hint-filtering reason at invoice creation. Follow-up on file: regtest integration test of the positive hint path; real LSPS2 JIT must prioritize the intercept SCID over capacity ranking.
- **LDK 0.1.0 WASM bindings can't reliably do custom peer messages (LSPS2-over-BOLT8) — the u16 message type is mishandled as a sign-extended int16.** Building an LSPS0 transport (peer msg type 37913 = 0x9419) on `lightningdevkit@0.1.0`: `CustomMessageHandler`/`CustomMessageReader`/`Type` are all implementable from JS via `.new_impl`, and our message goes out **spec-perfect and is verifiably transmitted** (LDK trace: `Enqueueing message lsps`), yet real mainnet LSPs (Megalith ×2, Olympus) **never reply**. **Proven binding bug:** calling `Type.type_id()` on a JS-impl'd Type whose id is 37913 returns **−27623** (sign-extended int16, since 37913 > 32767) — so the reader guard MUST compare `(t & 0xffff) === 37913`, not a strict `!==` (else every inbound msg is silently dropped), and the same corruption very likely hits the on-wire type on the WRITE path, so LSPs see a wrong type and ignore us. The reference LSPS client everyone (incl. AlbyHub) uses is LDK's **`lightning-liquidity` crate — NOT exposed in the WASM bindings**; newer `lightningdevkit` npm (`0.1.2-0` … `0.2.4-0`) is all **prerelease**. **Second trap:** `connectPeer` resolves on socket-open, **before** the BOLT8 handshake — sending a custom message immediately makes LDK drain it from the handler and **silently DROP it** ("no connection to the node exists, the message is simply not sent"), leaving your outbound queue empty. Gate the send on `peerManager.list_peers()` containing the pubkey (i.e. post-handshake). **Also:** bLIP-52 LSPS2 has ONLY `lsps2.get_info` + `lsps2.buy` — there is **no `get_versions`** (that was a non-standard regtest-dev-server extension; calling it gets no reply). All of this is parked on `feat/lsps2-jit-m1` with the analysis; JIT stays blocked until a stable (non-prerelease) LDK binding with working custom messages, or a `lightning-liquidity` WASM build, exists.
- **A browser's global `fetch` throws "Failed to execute 'fetch' on 'Window': Illegal invocation" if stored and called as an object method** (`this.fetchImpl(url)` sets `this` to the instance, not `window`, and `fetch`'s brand-check rejects it). This **only surfaces in the real browser** — tests inject their own `fetchImpl` and Node's `fetch` is lenient, so it passes CI + a Node smoke and breaks live (hit in the extension/PWA LSPS1 quote flow). Any client that takes an optional `fetchImpl` must default to **`globalThis.fetch.bind(globalThis)`**, never bare `?? fetch` (`lsps1-rest-client.ts`; also the lsps2-server lnd/bitcoind clients; regression test in `lsps1-rest-client.test.ts` simulates the brand-check by throwing when the receiver isn't `globalThis`).

## Testing Rules (Vitest)

- **TDD is mandatory:** red → green → refactor. No production code changes without corresponding tests in the same task.
- **Do NOT mock LDK internals** (`vi.mock('lightningdevkit')`, channel managers). Use the real LDK WASM library; mock the network socket transport or HTTP via **MSW** instead.
- **Do NOT mock the gateway DB.** Use a real isolated test DB (in-memory SQLite); truncate between suites.
- **Assert outcomes, not implementation** (node status transitions, persisted state, relay responses) — not private call order or log strings.
- Wallet tests run in `jsdom` (IndexedDB simulation); gateway tests run in `node`.
- Integration tests in `packages/libre-listener-wallet/src/tests/integration/` require the `docker compose` regtest stack (esplora on `:3002`, lnd LSP on `:9735`). Unit tests in `src/tests/unit/` do not.
- **Soak tests (`src/tests/integration/soak-*.test.ts`, docs `docs/soak-testing.md`) hunt force-closes + measure latency** — the tool for the fund-critical "state reset/collision/streaming" class. Each opens a channel, drives payments, restarts/wipes/hands-off, and reports every `[GOTCHA]` at the end (cycle counts env-configurable: `SOAK_CYCLES`/`NWC_CYCLES`/`VSS_RECOVER_CYCLES`/`BOOST_CYCLES`/`STREAM_*`/`MULTI_*`). Docker-gated, run manually. **A pass/fail soak isn't enough — `soak-nwc-streaming.test.ts` MEASURES per-payment latency (that's how the 26× streaming bug was found; every functional test passed straight through it).** `soak-crossdevice-handoff.test.ts` is `it.skip` documenting the LDK active-handoff limitation.
- **Storage-contract tests are special:** the `storage-contract.test.ts` files pin the on-disk format that funded wallets depend on. Never "fix" a failing assertion by editing the expected value — a failure means a persisted invariant changed (force-close / unrestorable-backup risk). Change the constant deliberately + add a migration + update the test in the same commit. They're wired into `pnpm check:storage` (which now runs the SDK, example-app, browser-extension, **and** wallet-pwa contract suites), the pre-push hook, and the deploy workflow (see the storage-contract guard above).

## Linting & CI

- **ESLint is real** — flat config at `eslint.config.mjs` (typescript-eslint, **type-aware** via `projectService`, so it resolves each package's own tsconfig). `pnpm lint` runs `turbo run lint`; each package has an `eslint src` lint script. Ignores `dist`/`public`/`node_modules`/`*.config.*`/`scripts`.
- **The async-safety rules are ERRORS and gate the build:** `@typescript-eslint/no-floating-promises` and `no-misused-promises`. In a wallet full of async payment paths an unhandled promise is a bug — mark an intentional fire-and-forget with `void`, or add a `.catch`. Don't suppress with `// eslint-disable` unless you can justify it.
- LDK-binding noise is turned **off** (`no-explicit-any`, `no-non-null-assertion`, `no-this-alias`, `no-empty-object-type` — the generated bindings force these). Pre-existing style debt (unused vars, empty catches, `prefer-const`) is left as **warnings** (non-blocking backlog); tests relax floating-promises/unused-vars. `pnpm lint` is currently green (0 errors).
- **CI: `.github/workflows/ci.yml`** runs on push + PR to `master` with least-privilege `permissions: contents: read`: **lint → check:storage → build → unit tests → typecheck**. The SDK's docker-backed integration tests are intentionally excluded (only the fast unit suites run: `vitest run src/tests/unit`); nothing deploys from this workflow. Keep it green.
